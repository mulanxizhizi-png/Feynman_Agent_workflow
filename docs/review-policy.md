# 审核启动策略

执行者 GPT-6 Sol / low；统筹审核者 GPT-6.1 Sol / high。调度上下文不能直接继承为首次盲审上下文，详见 [上下文协议](reviewer-context.md)。本策略决定何时启动，不认证模型能力或判断正确性。

## 先记录，后决定

按 [评估模板](../examples/review-assessment.example.json)记录改动、原始证据及事实依据，运行 bin/workflow.mjs decide。输入与结果放在任务runtime内。证据路径相对目标root，工具核对普通非空文件和SHA256；结果绑定规范化评估JSON哈希与策略版本。

工具确定性处理已申报事实，无法自动认证统筹的风险判断；不得把缺信息填为false。未知需继续调查，证据不齐时evidence_complete=false。改动行数和耗时不决定风险。统筹不能在失败后缩小合同、降低风险或启用免审来取得通过。

## 事实定义

readiness三项必须明确：stable表示待审生产文件不再同时修改；checks_passed表示当前版本必要自检已完成且通过；evidence_complete表示必要原始证据已取得，来源/状态/视口等元数据足够，无法判断项已识别。任何一项false输出prepare，不正式启动验收审核，也不能免审通过。

impact只要任一成立就不是免审微调：

| 字段 | 判断依据与例子 |
| --- | --- |
| behavior | 点击/键盘/状态/条件/错误处理/流程的可观察行为改变 |
| meaning | 业务事实、含义、操作时机、名称或权限说明改变；改一个字也可能成立 |
| layout | 排布、裁剪、密度、字体、图文关系、响应方式改变，需要实际渲染判断 |
| permissions_or_data | 认证、权限、数据处理、持久化、迁移、删除或外部写入边界改变 |
| shared_rules_or_dependencies | 公共组件、共享规则、配置/依赖、调用入口、目录/API兼容改变 |

纯注释修正、含义不变的拼写修正或可验证的机械整理可能全部false，仍须有原始差异与适当检查证据。文件少、字少不构成免审依据。

review条件：

- explicitly_required：用户或预先合同明确要求独立审核；永远不能用低风险免审覆盖。
- allow_low_risk_exemption：任务开始前已存在的项目/任务免审策略，须填写exemption_authorization原文或出处；没有策略时false。
- prior_review_valid：原始审核真实存在、合同标准和覆盖范围仍适用、独立性未失效，未解决项完整。合同变更或原报告身份/污染未验证时false。返工中的有效审核记录不等于当前版本已通过。
- prior_review_passed：旧报告在适用范围的必需条件已经通过，且独立性已核实。必须同时prior_review_valid=true；有效但失败/未验证的旧审核记录不能据此复用批准。
- revision_changed：与适用旧审核相比，合同、生产文件、相关证据或覆盖范围是否变化；任何变化true。只有完全相同且旧结论通过才能false；不能只比源码而忽略合同/截图。
- reviewer_context_available：原审核者仍保留相关材料；丢失材料、恢复或换人时false，旧登记不能代替上下文。
- contamination：在首次发现固定前暴露实现者评价/旧结论等禁止内容，或后来发现实际串用非自身上下文。
- co_design：审核者参与当前版本实现、共同决定实施方案、生成实施补丁或写目标生产文件。
- severe_miss：旧审核漏掉已证实的必需条件失败、权限/数据风险或关键任务不可完成；不是一般偏好分歧。
- material_dispute：双方对同一必需条件存在会改变验收结论的冲突，补证据后仍无法消解；仅审美建议不属于此项。缺证据先prepare。
- important_delivery：公开发布/部署、合入共享默认分支、跨项目分发，或权限/数据/公共接口/共享工作流策略的关键变更。普通本地草稿不是；当前范围已有覆盖最终交付的有效同版本终审时不重复启动。
- completed_rounds：本任务已经完成的正式审核轮数，包括未通过/污染失效的轮次；工具启动失败不算完成。新评估不能重置旧轮次，合同范围调整也保留累计记录。

## 决策优先级

1. 条件未齐：prepare。污染身份仍需立即记录并停止复用，只是先补齐版本再派新审核者。
2. prior_review_passed与prior_review_valid都为true，原通过结论对相同合同、冻结版本和交付范围仍有效且未有污染/共同设计/严重漏检/实质争议：reuse_approval。同版本旧报告未通过则prepare，先修复或补证据，不能重复引用为通过。
3. 需新审核且已有三轮：stop，报告剩余问题和限制，不宣布通过。明确的新任务另建ID，不能改ID规避原任务上限。
4. 污染、共同设计、严重漏检或实质争议：fresh_review。重要交付也fresh_review。
5. 有旧审核者：旧审核或上下文不可用则fresh_review；否则recheck，重验变化区、直接依赖、保留条件和全部旧问题。
6. 无旧审核者：明确要求则initial_review；所有影响均false且事先免审策略允许才self_check_only；其他initial_review。

initial_review/fresh_review需要新上下文。fresh_review并不自动增加第三个常驻审核者；替换原审核实例即可。三轮上限不是让统筹自行认定通过的权限。

## 为什么启动、为什么不启动

启动理由必须指向未被现有证据覆盖的影响、明确合同要求或独立性失效，不用“想更稳一点”无限增派。无需启动时说明是等待准备、同版本有效结论复用、已授权低风险自检或轮次停止；不能把这四种情况都叫“审核通过”。

统筹记录可核对的事实和理由，审核者独立核对合同/清单完整性及影响；发现错误申报按事实修正并保留原记录。分数仅诊断，不构成启动新审核或必须修复的依据。
