# 验证与发布方法

本文件描述可执行的验证方法，不保存历史通过结论。实际运行报告放在被忽略的 runtime/，首次审核不得接收旧报告或实现者自评。

## 本地验证

在仓库根目录运行 npm run validate，需 Node.js 22+、Python 3.11+。无外部 API 请求，无第三方依赖。

覆盖源码发布白名单、非空文件、JS/Python语法、JSON/TOML解析、相对模块引用、Markdown文件链接、常见凭据模式、Node回归测试、Python本地传输测试及MANIFEST完整性。凭据模式扫描不能证明无秘密，人工检查暂存差异和路径仍必要。

技能官方验证器仅在宿主已安装并具备其依赖时运行；不可用时报告工具限制。仓库验证涵盖技能入口链接，但不冒充官方技能行为认证。

## 清单更新

node scripts/manifest.mjs build 输出候选JSON到stdout，不覆盖现有MANIFEST。将候选写到runtime/，审查文件范围后用补丁更新MANIFEST.json。清单不包含自身、运行产物、凭据、缓存或产品文件。check模式核对实际路径、大小与SHA256，既检查遗漏也检查多余发布文件。

测试和运行产物写到临时目录或runtime/。Python使用AST语法检查，不生成源码目录内的pyc。

## 独立验收

先冻结源码、原始文档快照/参考和原始程序结果。源码与检查证据角色分开，实际阅读文档的结论不能仅引用程序测试成功。原始文档可作为reference证据，须实际阅读并核对来源。

按审核合同给出状态，附独立性证据；check退出0只表示结构/哈希一致。首次发现先固定，再读历史材料。审核期间生产文件变化即冻结失效，不修改文件后继续沿用旧版本通过结论。

## 上传范围

只提交MANIFEST列出的工作流源码和MANIFEST本身，并检查已跟踪旧路径的删除。用户授权上传不代表可以上传目标项目、本机运行记录或凭据。推送原远端时不强制覆盖；若远端有新提交先正常整合，再重新验证受影响内容。

GitHub Actions在Linux和Windows验证离线核心、兼容适配器和完整清单。可选Gemini连接检查只允许手动触发；日常push不会调用付费API。
